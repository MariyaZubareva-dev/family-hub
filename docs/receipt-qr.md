# Чеки по QR-коду

Фото декодируется локально через `zbarimg`. Поддерживаются фискальные строки российских кассовых чеков `t=…&s=…&fn=…&i=…&fp=…&n=…`. Произвольные ссылки из QR не открываются. Если на фото несколько разных фискальных QR, используется проверка по фото вместо выбора случайного чека.

Для фото с камеры сначала читается оригинал, затем при неудаче — три чёрно-белых варианта с разными порогами яркости и вариант с масштабированием/усилением контраста. Это позволяет читать мелкий QR на серой бумаге без скриншота с сайта. Обработка выполняется локально через имеющиеся GD/ZBar, без новых пакетов или API-токенов; исходное фото не меняется. У попыток общий бюджет 12 секунд, один процесс — до 4 секунд. На неудачном QR повторный цикл перед OCR не запускается. Очень размытый, обрезанный или засвеченный QR всё ещё может потребовать повторного фото крупнее.

Регрессионная камера-фикстура `fiscal-qr-camera.jpg.b64` создана из диагностического QR с тестовыми реквизитами: уменьшение до 160×160, лёгкое размытие, серый фон/ослабление контраста, JPEG. Пользовательские фото чеков в репозитории не сохраняются.

При найденном QR сервер передаёт в `https://proverkacheka.com/api/v1/check/get` только реквизиты и серверный токен, без фотографии. Источник контракта: https://proverkacheka.com/example/check.html.php. Перед промышленным включением необходимо проверить контракт, скорость, лимиты и условия коммерческого использования по документации в личном кабинете поставщика. Платные услуги автоматически не подключаются.

## Подключение

1. Получить собственный API-токен у proverkacheka.com по инструкции сервиса (заявка на webmaster@proverkacheka.com). Сверить лимиты и возможность использования в Family Hub. Бесплатность публичного сайта не означает бесплатность API.
2. Добавить `RECEIPTS_API_TOKEN` в серверный `.env.production`. Токен не добавлять в Git и не передавать в браузер. Публичные ошибки сервиса и диагностические ответы не сохраняются в чек.
3. Собрать backend, queue, scheduler и frontend. Применить миграцию `2026_10_22_000027_add_receipt_qr_lookup`, пересоздать контейнеры. В образ backend добавлены пакеты Alpine `zbar` и `imagemagick`: одних библиотек `imagemagick-libs` недостаточно для чтения PNG. Локальная разработка на Debian/Ubuntu требует `zbar-tools`.
4. Загрузить свой чек, сверить позиции и итог с оригиналом, проверить повторную загрузку и отсутствие повторных расходов. Реальные платные запросы требуют токена; автоматические тесты используют подмену HTTP.

Без токена приложение продолжает распознавать позиции по фото. Если QR прочитан, итог и дата берутся из QR. Старые чеки автоматически не отправляются провайдеру: для повторного анализа нужно нажать «Распознать ещё раз».

## Документы с линейным штрихкодом

Внутренний штрихкод магазина (например, Code 39 / Code 128 на товарном чеке «Ленты») не содержит обязательного набора фискальных реквизитов. Он не преобразуется в фискальный QR и не отправляется в API проверки чеков. Такой документ читается локальным OCR по тексту фотографии; новый токен не требуется. Электронные чеки «Лента» также предоставляет по email и в личном кабинете: https://lenta.com/i/info-lc/refusalprintreceipts/.

`ReceiptPhoto` выделяет светлую бумагу на уменьшенной копии до 320 пикселей, убирает фон вне её выпуклой оболочки и масштабирует область для OCR. Если подходящий лист не найден, сохраняется обработка полного изображения. Это эвристика для фото на контрастном фоне, а не гарантия определения любого документа. Два крупных раздельных светлых листа дают `review_reason=MULTIPLE_RECEIPTS`: позиции не объединяются, QR с другого чека на фоне не запрашивается, интерфейс просит отдельное фото одного чека. Несколько разных итогов в OCR также требуют нового фото.

Tesseract пробует режимы 6, 4 и 11 в общем бюджете 25 секунд. Выбирается один результат, списки товаров между проходами не складываются. Разбираются строки «название, цена × количество = сумма, НДС», весовое количество, «ИТОГО К ОПЛАТЕ» и дата с двухзначным годом. Раздельные OCR-колонки соединяются только при явной последовательности цена/множитель/сумма и всегда требуют проверки. Ошибки арифметики сохраняются для редактирования; налог, скидка и безналичная оплата не становятся товарами. Позиции с нулевой ценой и суммой исключаются из расходов как в OCR, так и в электронном чеке.

Версия `table-v4` проверяет направления 0/90/180/270° без зависимости от EXIF и модели OSD. Для длинной горизонтальной области сначала проверяется поворот на 90°, затем выбирается направление с читаемыми товарами. Дальнейшие режимы сегментации работают с выбранным направлением. Дата и итог могут дополняться из других проходов по тому же изображению; товары берутся из одного прохода. Разные прочитанные итоги/даты дают `TOTAL_UNCERTAIN` / `DATE_UNCERTAIN` и требуют проверки. Для бледного деревянного фона выполняется дополнительная проверка более нейтрального цвета бумаги, чтобы стол не попадал в область OCR. Мелкий шрифт и неверные цифры по-прежнему могут требовать редактирования: совпадение общей суммы не подменяется догадкой.

После обновления backend можно проверить версию и локальное чтение повёрнутого синтетического чека, без реальных фото и сетевых запросов:

```sh
docker compose --env-file .env.production -f docker-compose.prod.yml exec -T backend php artisan family:check-receipt-ocr
```

Ожидаются `OCR_VERSION=table-v6`, `OCR_ROTATION_OK=true`, `OCR_LONG_RECEIPT_PROCESSED=true` и код выхода 0. Команда проверяет и повёрнутый короткий чек, и выполнение OCR на длинном чеке с 80 товарами. Для длинного примера отдельно выводятся `OCR_LONG_ITEM_COUNT`, `OCR_LONG_TOTAL_READ`, `OCR_LONG_STATUS`: успешное выполнение процесса не означает безошибочное чтение всех цифр. Для `PROCESSED` нужны прочитанные товары, более 1000 символов OCR и хотя бы один проход с кодом выхода 0 без тайм-аута. Она временно отключает необязательный внешний vision-провайдер в своём процессе и восстанавливает настройку после проверки. В CI проверка запускается внутри production-образа с ограничением до одного CPU. Если команда отсутствует, запущен старый backend; обновить только Git недостаточно — нужны сборка и пересоздание контейнеров. Frontend пересобирается отдельно; старый текст «Повторите распознавание или добавьте позиции вручную» означает, что браузер использует прежнюю сборку интерфейса.

В `table-v6` длинный чек дополнительно читается восемью перекрывающимися фрагментами с локальным выравниванием строк. Принадлежность строки определяется координатами, поэтому одинаковые реальные покупки сохраняются, а перекрытие не дублирует их. Незавершённый проход по фрагментам отбрасывается; ранее прочитанный результат сохраняется. Выбирается один список товаров, списки разных проходов не склеиваются. Размер упаковки перед ценой не считается разделителем тысяч. Неоднозначный знак количества восстанавливается только по напечатанным цифрам и совпадению арифметики, с обязательной проверкой пользователем. Это улучшение OCR, а не гарантия точного чтения всех строк; QR остаётся первым источником данных.

В `table-v5` Tesseract запускается с `OMP_THREAD_LIMIT=1`, бюджет OCR увеличен до 35 секунд, лимит одного прохода — до 25 секунд. На одном ядре четыре OCR-потока могут замедлять работу и приводить к отбрасыванию результата по прежнему 10-секундному ограничению; рекомендация поставщика: https://tesseract-ocr.github.io/tessdoc/FAQ.html#can-i-increase-speed-of-ocr. При сбое последующего прохода уже прочитанные позиции сохраняются. При полном отказе возвращается `OCR_TIMEOUT` или `OCR_UNAVAILABLE`, интерфейс объясняет серверную проблему вместо предложения переснять чёткий чек. Журнал содержит только версию, режим, длительность, факт тайм-аута и код выхода; текст, изображения, ключи и реквизиты не записываются в диагностический журнал.

Диагностика конкретного сохранённого чека по ID или имени файла:

```sh
docker compose --env-file .env.production -f docker-compose.prod.yml exec -T backend php artisan family:check-receipt-ocr --receipt=IMG_8623.jpeg
```

Это локальное чтение сохранённого изображения без внешних запросов. Команда не меняет черновик и не создаёт расходы. Выводит `READ_ONLY`, число товаров, факт чтения итога, причину проверки, время и статистику попыток; названия товаров, сам итог, токены и фискальные номера не выводятся. В случае совпадения имени берётся последний неудалённый чек; ID позволяет выбрать запись однозначно.

Обрезанные или закрытые товары не восстанавливаются. Неполный список не считается успешно распознанным, пока сумма не совпадёт с итогом. Пользователь проверяет/исправляет данные перед подтверждением; фотографии и их содержимое не добавляются в репозиторий.

Проверка декодера после обновления (без обращения к API, токена и пользовательских данных):

```sh
docker compose --env-file .env.production -f docker-compose.prod.yml exec -T backend php artisan family:check-receipt-qr
```

Ожидаемый результат: `{"QR_DECODE_OK":true}` и код выхода 0. Команда читает тестовый QR через тот же путь, что и загрузка фото. CI выполняет её внутри готового production-образа от пользователя приложения. Ошибки запуска декодера записываются в журнал только с кодом выхода или типом исключения, без фото, реквизитов чека и токена.

## Обработка и состояния

- `READY`: получен электронный чек; итог сравнивается с QR, фискальные номера при наличии — с запросом, суммы строк — с итогом. Денежные поля провайдера переводятся из копеек в рубли. Неоднозначное произведение количества и цены помечается для ручной проверки.
- `WAITING` / `AWAITING_DATA`: пустой список позиций и точная сумма QR, фоновое ожидание. Команда `family:refresh-qr-receipts` запускается планировщиком раз в минуту, обрабатывает до пяти чеков за проход. Не более шести запросов на цикл с задержками 1, 5, 15, 60 и 360 минут. После лимита — `UNAVAILABLE` с ручным повтором.
- `NOT_CONFIGURED`: токен не указан, используется OCR.
- `INVALID_QR`: сервис вернул код 0 — реквизиты не подтверждены; автоматических повторов нет.
- `LIMIT_EXCEEDED`: код 3 или HTTP 429 — исчерпан лимит API; автоматических повторов нет. Коды 2, 4 и 5 означают ожидание данных с ограниченными повторами.
- `ACCESS_ERROR`, `INVALID_DATA`, `UNAVAILABLE`: требуется ручная проверка или повторный запрос. Технические сообщения и токен пользователю не показываются.
- `UNSUPPORTED`: операция отличается от покупки (`n=1`); подтверждение расхода блокируется. Автоматический учёт возвратов не реализован.
- `MANUAL`: пользователь сохранил правки ожидающего чека; фоновые запросы больше не меняют черновик. Удалённые и подтверждённые чеки также не обновляются.

Фоновые изменения сравнивают статус, число попыток и версию времени обновления перед записью. В интерфейсе открытый ожидающий чек проверяется каждые 15 секунд до получения данных; локальный ввод останавливает это обновление.

Дубликаты определяются по хешу ФН + ФД + ФП только внутри семьи. Существующий чек открывается вместо создания повторных расходов. Уникальный частичный индекс страхует параллельные загрузки. Удалённый черновик можно загрузить заново. Для старых чеков без сохранённого QR-отпечатка автоматический поиск дубликатов не выполняется. Категории берутся из существующего списка Финансов и остаются редактируемыми; расходы создаются только после подтверждения.

## Подбор категорий товаров

После получения позиций через QR/API, фото/OCR или фоновый запрос применяется `ReceiptCategoryMatcher`. Он выбирает только активные, неудалённые расходные категории текущей семьи и не создаёт новые категории.

Сначала учитывается последний подтверждённый выбор для точно такого же нормализованного названия товара: регистр, «ё», пунктуация и пробелы не влияют на сравнение; размеры, марки и числовые значения сохраняются. Рассматриваются последние 2000 операций по подтверждённым, неудалённым чекам семьи. Черновики, чужие семьи и недоступные категории не используются. Это повторение подтверждённых решений, а не обучение внешней модели.

Если совпадения в истории нет, применяются точные названия пользовательских категорий и локальные правила для продуктов, лекарств/медицинских услуг, бытовых товаров, одежды и других поддержанных групп. Например, молоко относится к существующей категории «Продукты», ибупрофен — к «Здоровье». Поддержаны известные синонимы названий категорий; произвольные названия и незнакомые товары правила могут не определить.

Неоднозначные позиции получают `category_needs_review=true` и существующую общую категорию «Покупки»/«Другое»/«Прочее». При отсутствии общей категории поле остаётся пустым — пользователь выбирает категорию перед подтверждением. Числа, названия позиций и флаги проверки сумм не меняются. Категории можно исправить в списке и редакторе позиции; выбор используется для следующих чеков только после подтверждения расходов. Запросов к дополнительным внешним сервисам и платежей за подбор нет. Старые черновики автоматически не пересчитываются; повторное распознавание применит подбор заново и заменит текущие правки черновика.
