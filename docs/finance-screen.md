# Финансы

Экран финансов вынесен в `frontend/src/FinanceScreen.tsx`, стили — в `finance.css`. Компонент «Семья» и `styles.v07.css` не менялись.

- Категории хранятся с `transaction_type=EXPENSE|INCOME`; существующие категории сохраняют тип EXPENSE. Стандартные доходы: ЗП, Премия, Другое. Категории создаёт администратор через POST `/api/v1/finance/categories`, доступны всем членам семьи с доступом к финансам. Категории показываются даже без операций. Повторное чтение не создаёт дубликаты.
- POST `/api/v1/finances` принимает `category_id`; сервер проверяет семью, тип и название категории. Аналитика и история обновляются после сохранения.
- Чеки: фото JPEG/PNG/WebP уменьшается перед загрузкой; backend проверяет изображение и ограничивает размер до 8 МБ. Tesseract с русским и английским языками установлен в backend image. Распознанные позиции требуют проверки; нераспознанное фото остаётся черновиком. При наличии OPENAI_API_KEY применяется дополнительно настроенная модель OPENAI_MODEL. Без ключа работает локальный OCR. Повторное распознавание: POST `/api/v1/finance/receipts/{id}/retry`. Черновик можно сохранить и открыть из истории. Подтверждение создаёт расходы по позициям в транзакции с блокировкой чека. Повторное подтверждение возвращает 409.
- Кредит/рассрочка: POST `/api/v1/credits`, `type=CREDIT|INSTALLMENT` (у старых записей CREDIT). Рассрочка имеет нулевую ставку. Члены семьи с доступом к финансам читают кредиты, изменяет только администратор. Досрочные платежи и выбранное назначение сохраняются; суммы по договору не выдаются за автоматически пересчитанный банковский остаток. Внесение досрочного платежа не дублирует операцию расхода.
- Регулярные покупки находятся в разделе «Покупки». В финансах вместо дублирующей вкладки «Запасы» доступен экран «Мои» с доходами и личными копилками.
- Бюджет сохраняет месячный общий лимит и лимиты расходных категорий. Категории проверяются до изменения бюджета; запись выполняется в транзакции.

## Обновление

Сделать резервную копию БД. Собрать backend, queue, scheduler, frontend, backend-nginx. До перезапуска выполнить `docker compose --env-file .env.production -f docker-compose.prod.yml run --rm --no-deps backend php artisan migrate --force`. Затем пересоздать сервисы. Миграция `000022` добавляет типы категорий и кредитов без изменения существующих операций. Автоматический откат миграции намеренно запрещён: после создания одноимённых категорий разных типов восстановление прежнего уникального ограничения требует отдельного объединения данных.

## Проверки

`npm run build`, `npm run test:ui`; backend `vendor/bin/phpunit` (для теста реального распознавания нужны tesseract-ocr и языки rus+eng). Проверки интерфейса используют управляемый API; отдельные backend-тесты проверяют фактическое сохранение в БД, категории, права, чек и бюджет. Сценарии «Семьи» входят в тот же прогон.

## Проверка распознавания многострочных чеков

Для мелкого текста backend увеличивает изображение до двух раз средствами GD (до 3200 px по длинной стороне), сохраняя промежуточный PNG без потерь. Нумерованные блоки товаров разбираются как название с переносами, количество × цена и стоимость позиции. Итог, НДС и оплата исключены из позиций. Несогласованное количество или сумма дают NEEDS_REVIEW.

В JSON чека `receipt_total` хранит прочитанный/уточнённый итог отдельно от рассчитанного `total` позиций. PATCH сохраняет оба значения; POST confirm проверяет их совпадение на сервере. Уточнить итог можно в «Данных чека». Неизвестный итог и расхождение блокируют подтверждение; черновик можно сохранить. В существующих неподтверждённых чеках доступно повторное распознавание по сохранённому фото. Для обновления нужна пересборка backend image с GD и frontend, миграций нет.

Проверка чека показывает компактные строки; редактор открывает одну позицию. Снимки и проверки выполняются при 320, 393 и 768 px. Фикстура numbered-receipt.txt содержит только строки позиций и суммы, без контактных и фискальных данных исходного чека.

## Личные финансы и копилки (октябрь 2026)

В разделе «Финансы» есть переключатель «Семейные / Мои». В семейном разделе сохранены обзор, общая история доходов, категории, чеки, кредиты, лимиты бюджета и кешбэк. Дублирующая вкладка «Запасы» удалена; регулярные покупки остаются в «Покупках».

«Мои» содержит доходы текущего пользователя и его личные копилки. Доходы остаются общими для семьи и видны с автором. Названия, цели, остатки, начальные накопления, заметки и переводы между копилками доступны только владельцу, включая серверные проверки: администратор семьи не получает доступ к чужой копилке.

При добавлении дохода можно выбрать свою открытую копилку и сумму (не больше дохода). Сохранение дохода и перевод выполняются атомарно. Изменение старого дохода пересчитывает доступную семье сумму, но не отменяет уже совершённые переводы. Форма предупреждает об этом.

Доступно на общие расходы = внесённые доходы по сегодняшнюю дату − внесённые расходы по сегодняшнюю дату − переводы в копилки + возвраты из копилок. Расчёт использует `finance_transactions`, как действующая аналитика. Он не зависит от выбранного периода и переносится между месяцами. Месячные доходы, расходы и «Разница за период» остаются отдельной статистикой; лимиты бюджета не являются остатком денег. Будущие обязательства автоматически не резервируются. На главной отображается тот же текущий показатель.

Это остаток по внесённым операциям, а не банковская сверка: если история неполна, сумма также будет неполной. Начальный общий остаток/сверка счетов в этой версии не вводятся. Нельзя выдавать этот показатель за проверенный баланс всех банковских счетов.

При создании копилки «Уже накоплено» означает деньги, ранее не учтённые в семейном бюджете. Они не считаются доходом и не уменьшают бюджет. Если деньги уже внесены как доход, нужно создать пустую копилку и пополнить её из бюджета. Возврат любых средств из копилки увеличивает доступную семье сумму.

Операции копилок:
- `OPENING`: начальные личные накопления (в том числе 0).
- `DEPOSIT`: из бюджета в собственную копилку, в пределах доступного бюджета.
- `WITHDRAW`: из собственной копилки в бюджет, в пределах её остатка.
- `TRANSFER`: между двумя своими открытыми копилками, без изменения бюджета.

В разделе «Мои копилки» действие «Перевести между копилками» открывает прямой перевод. История каждой копилки показывает исходящий перевод со знаком минус и входящий со знаком плюс, с датой и названием второй копилки; заметка видна только владельцу. Переводы не создают доходов/расходов. Остатки вычисляются по истории, суммы проверяются до копеек. Изменять остаток напрямую нельзя. Для исправления перевода делают обратный перевод. Копилка закрывается только при нулевом остатке, история остаётся в архиве. Достижение цели ничего автоматически не переводит. Фактические расходы могут сделать общий остаток отрицательным; средства копилок автоматически не расходуются.

API:
- `GET /finance/personal`: только свои копилки, доходы, история и текущая доступная семье сумма.
- `POST /finance/pots`: название, необязательные цель/дата, начальная сумма, UUID `request_key`.
- `PATCH /finance/pots/{pot}`: название/цель/дата; null очищает цель и дату.
- `POST /finance/pots/{pot}/movements`: вид, сумма, для перевода `destination_id`, необязательная личная заметка, UUID `request_key`.
- `POST /finance/pots/{pot}/archive`: закрыть пустую копилку.
- `GET /finance/savings-history`: последние 100 пополнений/возвратов семьи с суммой и автором, без IDs копилок, целей и заметок.
- `POST /finances`: необязательные `savings_pot_id`, `savings_amount`, `request_key`. Для резервирования все три обязательны; будущий доход резервировать нельзя.
- `GET /finance/analytics`: добавлено `available_cash`, прежнее `balance` сохранено для совместимости как разница за период.

Миграция `2026_10_29_000035_create_personal_savings.php` добавляет таблицы копилок/переводов и ключ повторной отправки дохода, не изменяет существующие денежные записи. Переводы сериализуются блокировкой строки семьи; повтор запроса с тем же UUID не проводит его повторно. Используется существующий доступ к разделу финансов; при скрытом разделе личные финансы тоже недоступны. Копилки связаны с пользователем и семьёй: перед выходом из семьи следует вывести накопления; перенос между семьями не реализован.

Проверки: `PersonalSavingsTest` проверяет изоляцию владельцев и семей, отсутствие доступа у администратора к чужим копилкам, расчёт при смене месяца, начальные накопления, атомарность дохода с переводом, повторные запросы, лимиты, архивирование и скрытый раздел. `personal-finance.spec.ts` проверяет экран, переводы, создание/архив, сохранение ошибки и мобильную ширину.
